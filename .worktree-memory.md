## Step 5 — automatic recap (COMPLETE)

`apps/server/src/services/threads/recap-auto-trigger.ts`. Hooked at
`apps/server/src/internal/events.ts` where `turn/completed` yields
`isRootTurnCompletion` — fire-and-forget, only for **completed root** turns
(interrupted/failed turns describe a state the thread is about to leave).

Policy is a pure function, `shouldAutoGenerateRecap`, checked cheapest-first:

1. `recapEnabled` false → stop. **The cost gate.** A thread whose recap nobody
   opened costs one indexed read per turn and nothing else.
2. `recapSourceSeq === maxSeq` → stop (already current).
3. inside `RECAP_AUTO_MIN_INTERVAL_MS` (3 min) → stop.
4. enabled but no recap yet → generate now (don't make the user wait 4 turns).
5. `completedTurns >= RECAP_TURN_CADENCE` (4) OR any salient event → generate.

Salient events = `thread/goal/updated` + `thread/goal/cleared`, counted by
`countThreadRecapTriggers` in `packages/db/src/data/thread-notes.ts` (two queries
on the `events_thread_type_sequence_idx` covering index). The turn count is the
guarantee; salience is only an accelerator.

`inFlightThreadIds` (process-local Set) stops overlapping generations — event
ingestion can process several turn completions back to back. Racing servers would
waste one call, not corrupt state; every recap is regenerable.

**What opens the gate:** `POST /threads/:id/notes/recap` calls
`enableThreadRecap`. `NotesPanel` posts once per mounted thread when the Recap
section is expanded. An already-current recap returns untouched (two reads), so
the request is cheap and doubles as "this thread's recap is worth maintaining".

### Design error worth remembering

I first added a 10s post-generation cooldown on `force`. Three existing tests
caught it, and **the tests were right**. `force` means "I disagree with this
recap, try again", and the likeliest moment to press refresh is immediately after
reading a bad one — the cooldown blocked exactly the legitimate case while barely
touching abuse. Removed it; the in-flight guard is the real anti-hammer, bounding
throughput by generation time rather than a timer. No test was modified.

## PARKED IDEA — Part 2: the grouped-list rail

Captured from a Synara screenshot Amir shared. Pick this up in the environment

### What Synara's rail actually is

Not a thin icon rail — a **~280px grouped list panel**. Sections with muted headers,
each containing icon+label rows. Order in the screenshot:

```
[control bar]  ⇄ Hand off | ▶ dev ⌄ | panel toggles
Environment ⚙   Changes · Worktree · feat/branch-name ⌄ · Pull ⌄ · Local Servers  0 ⌄
Repository      Emanuele-web04/synara ↗
Pull request    #574 Cache provider usage serv… ↗
                +464 −63  17 files ↗
                ⓘ Couldn't load PR data  ⟳
Editor          Editor view · Open in Finder ⌄
Recap ⌄         <generated prose paragraph>
```

### The row grammar (this is the whole design — copy it exactly)

Every row is icon + label on the left, and **one** of four things trailing:

| Trailing | Meaning          | Example                        |
| -------- | ---------------- | ------------------------------ |
| `↗`      | leaves the app   | repo link, PR link             |
| `⌄`      | expands in place | branch, Pull, Open in Finder   |
| count    | quiet state      | `Local Servers  0`             |
| nothing  | plain action     | Changes, Worktree, Editor view |

### Amir's hard constraint: NO BADGES

The mechanism that makes it work: **state lives in the trailing slot as a number or
text, never as a colored dot.** `Local Servers 0` communicates "nothing running"
without shouting. The single real failure gets a **full row** — red ⓘ + message +
retry icon — not a badge.

Rule to hold: _errors get a row, states get a number, nothing gets a dot._

### Why this is cheap in bb

bb already has every row. This is a **restyle + relocate**, not new data plumbing.

- `apps/app/src/components/secondary-panel/ThreadMetadataContent.tsx` (~36KB) contains
  `EnvironmentRow`, `WorkspacePathRow`, `BranchRow`, `PullRequestRow`, `MergeBaseRow`,
  `ForksRow`, `ParentSelectorRow`.
- `+464 −63 17 files` equivalent: `apps/app/src/components/workspace/workspace-change-summary.tsx`
- Changed files detail: `apps/app/src/components/workspace/ChangedFilesDetailRow.tsx`

Work is: (1) re-grammar those rows into the four-trailing-slot vocabulary under
collapsible section headers, (2) wire rows with a bigger surface to open the wide
panel tab — `Changes` → `git-diff` (deep-link atom `pendingGitDiffScrollPathAtom`
already exists), PR rows → `pull-request` tab, `Local Servers` → `browser` tab.

### The one row bb has no data for

**`Local Servers`** — dev-server/port liveness. `EnvironmentRow` shows _configuration_,
not liveness. This is Amir's Vercel + localhost plugin integration, and it's the right
first consumer of a new **`experimental_railItem` plugin slot** (alongside the existing
`threadPanelAction` in `packages/plugin-sdk/src/app-contract.ts`) rather than hardcoding
provider knowledge into core. Per the Plugin API rule: ships `experimental_`-prefixed
with an entry in `docs/api_to_audit.md`.

### Known costs / open risks

- Always-visible ~280px permanently narrows the timeline. Validate against Amir's real
  laptop width before committing.
- Collapsible section state needs per-thread persistence — more tab-state surface.
- Synara's `▶ dev ⌄` run control means their rail both **shows and controls**. That's
  what makes `Local Servers 0` meaningful. A read-only bb version is strictly weaker;
  consider whether run-control is in scope.

## Reference: findings that took real digging (don't re-derive)

### Sidebar styles are plugins, and conductor "tabs" ARE bb threads

- Sidebar list provider is a plugin slot: `experimental_threadList`.
  Preference atom: `apps/app/src/components/sidebar/threadListProvider.ts`
  (localStorage `bb.sidebar.threadListProvider`, client-local by design).
- Conductor-style sidebar = `plugins/conductor-workspaces/`, registers thread list
  id `conductor`, titled "BBamir" — "Repositories, workspaces, and conversation tabs."
- `plugins/conductor-workspaces/src/projection.ts`: `ConductorWorkspace.threads` is
  `readonly PluginSidebarThread[]`, and a workspace maps to an environment.

**Therefore: a conductor "tab" is a bb thread.** Both sidebar styles key on `threadId`.
Any per-"tab" state is per-thread state — no per-style storage divergence needed.
Only breadcrumb/labels differ (`AppBreadcrumbs.tsx`, `ConductorContextBar.tsx`).

### Recap cannot be derived — it must be generated

`useThreadConversationOutline` (`apps/app/src/hooks/queries/thread-queries.ts:857`,
contract `packages/server-contract/src/api/threads.ts:796`) returns
`{ id, role, preview, attachmentSummary }[]` + `maxSeq`. **`preview` is raw truncated
message text, not a summary.** It feeds the TOC minimap. Synara's recap is synthesized
prose ending in a next step — an LLM call, not a concatenation.

Existing harness to reuse: `apps/server/src/services/threads/title-generation.ts` uses
`inferenceComplete` from `apps/server/src/services/ai/inference.ts` with structured
output (`Type` from `@earendil-works/pi-ai`) and a timeout budget
(`MANAGED_THREAD_METADATA_TIMEOUT_MS = 2500`, 2 attempts) — see
`thread-metadata-inference.ts`.

### Tab state is SERVER-persisted and synced — the mobile trap

`packages/db/src/schema.ts:574` `thread_tabs` = `{ threadId PK, tabsJson, revision,
updatedAt }`. So a tab opened on desktop **arrives in the PWA's state**.

To hide a tab from mobile: **filter at render; never prune from state.** A prune writes
a new revision and deletes the desktop tab.

PWA gate: `apps/app/src/hooks/useStandaloneCompactPwa.ts` (handles both
`(display-mode: standalone)` and legacy iOS `navigator.standalone`).

### No protocol bump needed

Notes/recap live in the server DB; the host daemon never sees them. No
`HOST_DAEMON_PROTOCOL_VERSION` change. (Earlier assumption to the contrary was wrong.)
